# イベント投票の運用

このシステムは Next.js + Turso + Cloudflare Turnstile で構成されます。公開投票は `/`、Google管理者画面は `/admin` です。

## 新しいDBを初期化する

旧データを引き継がず、Tursoに新しい空のデータベースを作成してください。
`db/schema.sql` が**唯一のスキーマ定義**で、全部で10テーブルです。
初期化・検証には `.env.local` に接続情報を設定したうえで次を実行します。

```sh
node --env-file=.env.local scripts/setup-db.mjs
node --env-file=.env.local scripts/setup-db.mjs --check
```

初期化は空のデータベースに限ります。既存テーブルへの列追加・テーブル統合・投票履歴の移行は行いません。初期化はトランザクションでまとめて実行され、失敗時はロールバックします。

## 投票フローと不正対策

- 256ビットのランダムな署名付きHttpOnly Cookieを投票者に発行します。セッションごとに同一部門の候補へ投票できる上限は `polls.max_votes` です。
- 投票は `votes` **1テーブル**に保存し、`(poll_id, voter_hash, candidate_id)` の複合主キーで同一候補への二重投票を拒否します。定員・受付日時・候補の存在・重複検知は一つの原子的なINSERTで確認します。
- Turnstileをサーバーで検証します。トークンは使い捨てです。設定されていないと投票はできません。
- Vercelの信頼できる `x-vercel-forwarded-for` とCloudflare Workersの `CF-Connecting-IP` だけをIP取得に利用します。一般の `x-forwarded-for` やブラウザ送信値は信頼しません。生IPはDBに保存しません。
- IPと画面サイズ・倍率・OS種別・言語・タイムゾーンなどの端末情報のHMAC-SHA256を、重複の疑いの検知と連続送信の制限に利用します。ブラウザのUser-Agentは端末情報の照合から除外します。5分あたりセッション単位12回、IP＋ブラウザ情報単位40回を上限としてTursoで原子的に更新します。IP単独では拒否しません。
- `VOTE_MATCH_MODE=block` が既定です。IP＋ブラウザ情報が一致した再投票を拒否しますが、同型端末・共有Wi-Fiで誤判定があり得ます。必要に応じ `monitor` にして記録のみ行ってください。
- 同じ端末でも設定差で見逃したり、同じネットワーク上の同型端末で誤判定したりする場合があります。別のブラウザで設定が異なる場合は検知できないことがあります。
- 同一人物が別のネットワークを使う、VPNを使う、情報を偽装する行為を完全に防ぐことはできません。厳格な1人1票が必要なら来場者ごとの一意な資格が必要です。

## 正式票と条件判定専用の記録

`votes` 1テーブルに1選択1行で記録し、`is_official=1` が正式票、`is_official=0` が条件判定専用の記録です。後者は正式な票数・ランキングには加算せず、本人の進行状況や引換条件には1回分として反映します。信号一致によって条件専用になった部門では追加投票できません。`signal_match=1` は疑わしい一致の検知記録でもあります。

同じIP・端末情報による一致は本人確認ではありません。誤判定の可能性があり、条件付き引換の不正防止には別途本人確認が必要です。認証失敗、受付期間外、送信制限は進行状況に加えません。

**DBは新規作成専用**です。既存スキーマへの変更SQL・互換コードは含めません。

## 引換権と管理画面

管理者はGoogle OAuth 2.0でログインします。引換権は来場者の画面で一度だけ「引き換える」を押す方式です。コードの発行や2段階の受け取り操作はありません。条件判定は画面表示時に必要な当人の投票履歴を参照し、実際の引換確定時にはSQLの中で再判定します。

## Tursoの負荷削減

- 部門・候補・ページ構成・テーマ設定・公開アクションは30秒間、Worker/Nodeインスタンス内でキャッシュします。公開設定の変更は最大約30秒遅れて見える場合があります。実際の投票受付日時と公開設定はSQL側で毎回確認します。
- 投票者の投票履歴や引換権は共有キャッシュに入れず、`votes_voter` と `action_claims_voter` のインデックスで読み込みます。通常票と条件判定専用票は同時取得できます。
- 条件付きアクションは本人の履歴をまとめて取得し、件数に比例した個別クエリを実行しません。
- レート制限の2つのカウンターは1回のSQL UPSERTで更新します。
- 管理画面の候補別集計は`candidate_totals`、引換件数は`action_totals`から読み取ります。投票のINSERT/DELETEと同一トランザクション内のトリガーで更新するため、集計時に全票を走査しません。集計高速化と引き換えに正式票ごとにカウンタの1行更新が必要です。
- 小さい固定データは読み取りバッチと30秒キャッシュを利用します。通常の投票は1回のINSERT RETURNINGで正式票・条件専用票を確定します。
- 5分のレート制限カウンタはセッション・端末信号の2行を1回の原子的UPSERTで更新します。古い履歴は `node --env-file=.env.local scripts/prune-db.mjs` で削除できます（定期実行推奨）。

## 保守・プライバシー

IPとブラウザのハッシュ値も、必ずしも匿名情報とは言えません。来場者への利用目的の説明と保管期間・アクセス権限の管理が必要です。投票期間が終わったら識別情報を削除する運用を設けてください。例として、30日経過した投票のIP・ブラウザ情報を削除できます。

```sql
UPDATE votes SET ip_hash=NULL, fingerprint_hash=NULL
WHERE created_at < strftime('%Y-%m-%dT%H:%M:%fZ','now','-30 days');
DELETE FROM vote_request_limits
WHERE bucket < CAST(strftime('%s','now') AS INTEGER) / 300 - 2;
```

本番公開前は `npm run check` と `npm run cf:build` を実行し、複数端末・同一Wi-Fi・連続送信・候補数上限・景品引換を検証してください。
